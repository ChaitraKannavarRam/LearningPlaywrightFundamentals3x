Playwright

Architecture in Simple Words

A quick memory map for the full browser automation flow.

One-liner: Your test tells Playwright what to do, Playwright sends that instruction to the browser, and the browser performs the action like a real user.
1

Test File

Your code says: open page, click, type, assert.

2

Runner

Finds tests and starts workers.

3

Client SDK

Turns actions into messages.

4

Driver

Checks if the element is ready and waits smartly.

5

Browser Protocol

Talks to Chrome/Firefox/WebKit.

6

Renderer + DOM

The page runs and the real click happens.

7

Result

We get a response and the test continues.

Waits automatically Works across browsers Uses real browser events More reliable than sleeps
T

Test file

This is where your test logic lives: open page, click button, fill form, check result.

R

Runner

The runner is the manager. It finds tests, starts browser workers, and collects outcome data.

C

Client SDK

Playwright converts commands like page.click() into messages that travel to the driver.

D

Driver

This is the smart layer. It checks visibility, stability, and readiness before clicking.

B

Browser

Playwright talks to the browser through a protocol like CDP, so browser differences are hidden.

P

Page / DOM

The page renders the UI, the DOM is built, and the real click reaches the correct element.

The easiest way to remember Playwright is this: Test → Runner → SDK → Driver → Browser → DOM → Result.

The driver is the most important part because it does the smart waiting and checks before acting. That is why Playwright is usually more stable than tests that use hardcoded sleeps.

Think of it like a delivery chain:
Test code gives the order, runner manages it, driver decides the route, browser does the work, and the page gives the outcome back.
